# Security Features

This page describes the security controls of the [Educational Course Content Generator with QnA Bot using Bedrock](../README.md) sample, including their known limitations. File names such as `qna_stack.py` refer to the CDK stacks in `educational_course_content_generator_with_qna_bot_using_bedrock/` and to the Lambda sources in `lambda/`.

The application implements multiple layers of security:

- AWS WAF protects both CloudFront distributions with AWS managed rule groups (IP reputation, known bad inputs, SQL injection, Linux, Unix), a GeoMatch allow list and a rate limit of 100 requests per five minutes per IP.
- Amazon CloudFront provides built-in DDoS protection, enforces HTTPS for viewers, writes standard logs to the access-logs bucket and is the only intended entry point (the `execute-api` endpoints bypass WAF).
- CloudFront TLS versions: both distributions use the default `*.cloudfront.net` certificate, for which CloudFront applies its `TLSv1` security policy, so viewers can still negotiate TLS 1.0 and 1.1 although HTTPS is enforced. The `TLS_V1_2_2021` minimum protocol version that the stacks set only takes effect once you configure a custom domain with an AWS Certificate Manager (ACM) certificate; this is the documented `AwsSolutions-CFR4` cdk-nag suppression, to revisit before production use.
- Amazon Cognito handles user authentication with an explicit password policy (minimum 8 characters with upper-case, lower-case, digit and symbol) and ID tokens valid for 24 hours; self sign-up is disabled, so only an administrator can create users (as `scripts/create_cognito_user.py` and the demo do); MFA is optional and the Cognito Plus feature plan is not enabled (documented cdk-nag suppressions to revisit before production use).
- JWT-based Lambda Authorizers validate every `$connect` request: the token must come from the `Authorization` header (query-string tokens are rejected), be an RS256-signed Cognito ID token verified against the user pool's JWKS with the expected audience, issuer, expiry and subject, and any failure denies the connection (fail closed). The authorizer forwards the caller's `sub` and `username` to the routes, and the QnA proxy rejects requests without an authenticated subject (401).
- QnA conversations are isolated per authenticated user and course: the AgentCore session id is derived from the Cognito `sub`, so clients cannot choose or join another user's session.
- Amazon Bedrock Guardrails are applied to the QnA bot in both modes: content filters at HIGH strength for hate, insults, sexual content, violence and misconduct on input and output, prompt-attack detection at HIGH strength on user input (the service requires NONE on output for this filter), PII handling (e-mail addresses and phone numbers anonymized, credit/debit card numbers blocked, a 10-digit account-number pattern anonymized), the denied topics `IllegalActivities` and `PersonalizedFinancialAdvice`, and the PROFANITY managed word list. Blocked requests receive the guardrail's configured message instead of an answer.
- Guardrail policy changes must be accompanied by a bump of `GUARDRAIL_CONFIG_REVISION` in `qna_stack.py`: `AWS::Bedrock::GuardrailVersion` snapshots the configuration only when the version resource is created, so the new description publishes a fresh version and the `GUARDRAIL_VERSION` environment variable follows it. The `PersonalizedFinancialAdvice` denied topic is evaluated on student input only; evaluating it on model output truncated legitimate course answers about investment strategy during testing. In Strands mode the guardrail screens each new question when it arrives and every answer (`guardrail_latest_message` in `agentcore_handler.py`). The earlier turns of the conversation are not screened again as input, because an earlier answer about investment strategy would otherwise trip that denied topic and block every follow-up question of the conversation. A blocked question is replaced by a placeholder in the conversation history, so it does not reach the model on later turns, and a question whose model call fails is removed from the history. Screening one question at a time has a cost: a request that is spread over several turns, or that is recognisable only together with an earlier turn, is evaluated piece by piece. Prompt-attack detection and the `PersonalizedFinancialAdvice` topic are evaluated on input only, so for such a request the remaining safeguards are the agent's instructions (answer only from the retrieved course materials, ignore instructions embedded in a question) and the server-side course and week filter of the search tool; the policies that are enabled on output (content filters, `IllegalActivities`, PII handling, word filter) still screen every answer. A question in which the guardrail only anonymized an e-mail address, phone number or account number is not replaced: it stays in the session history as typed and is sent to the model with the history on later turns of that conversation. Review these trade-offs before you reuse the setting in an application with stricter requirements.
- The OpenSearch Serverless collection is private: its network policy allows access only through the `course-content-coll-vpce` VPC endpoint in the VPC's private subnets (used by the index-creator Lambda) and from the Bedrock service, so OpenSearch Dashboards is not reachable from the internet; a data access policy limits the collection to the Knowledge Base role and the index-creator role, and IAM/SigV4 authentication is always required. `QnAStack` requires the VPC created by `CourseStack` and refuses to synthesize without it, so there is no public fallback for the collection.
- Prompt hardening: the system prompts of the course generators and the agent are static, request fields reach the model only through the user message, the agent is instructed to answer only from retrieved course materials and to ignore instructions embedded in questions, and the course generators read input documents only from the solution's input bucket; retrieved passages are labelled with their document title, so QnA answers do not disclose S3 bucket names or object keys.
- Input validation on every route with generic error messages; Lambda logs contain only request metadata (route, connection id, request id, course id, week number and text lengths), never questions, answers, tokens or generated content; the AgentCore Runtime's traces and logs carry span metadata only: the Strands tracer redacts prompt, completion, tool-call and system-prompt content (`OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_unredacted_attributes=`), the botocore Bedrock instrumentation does not capture Converse messages (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=false`) and ADOT redacts the `gen_ai.*` content attributes before export (`AWS_REDACT_SPAN_ATTRIBUTES`).
- AWS IAM policies enforce least privilege: the proxy Lambda can only invoke the AgentCore Runtime, post to the WebSocket connections and send its own trace segments to AWS X-Ray; the AgentCore execution role can invoke the configured Claude model family, call `bedrock:Retrieve` on the Knowledge Base and `bedrock:ApplyGuardrail` on the guardrail, and has `logs:PutResourcePolicy` on the log groups of its own runtime only, which AgentCore needs to deliver the trace spans there; the Classic Lambda holds the equivalent `Retrieve`/`RetrieveAndGenerate` permissions and, in addition, `bedrock:GetInferenceProfile` on the Claude inference profiles of the configured prefix (`inference-profile/us.anthropic.claude-*` for the default model id), because `RetrieveAndGenerate` resolves the cross-region inference profile before it invokes the model; the Knowledge Base sync Lambda can only call `bedrock:ListIngestionJobs` and `bedrock:StartIngestionJob` on the Knowledge Base and consume messages from the sync queue, and Amazon S3 has no permission to invoke it.
- Encryption and network controls: S3 buckets block public access, use SSE-S3, enforce TLS and write server access logs; the course generation work queues use a customer managed KMS key with rotation, the Knowledge Base sync queue and its dead-letter queue use SQS-managed encryption (SSE-SQS), and all queues enforce TLS; the policy of the sync queue lets Amazon S3 send messages only on behalf of the Knowledge Base bucket in your account (it matches the bucket ARN with `aws:SourceArn` and, because a bucket ARN carries no account id, the account with `aws:SourceAccount`); DynamoDB tables use AWS managed encryption with point-in-time recovery; the OpenSearch collection is encrypted with an AWS-owned key; the log groups of the stacks use the default encryption at rest of CloudWatch Logs; the API Lambda functions run in the private subnets of the VPC and reach S3 through a gateway endpoint; VPC flow logs are enabled.
- `cdk synth` runs the cdk-nag `AwsSolutions` checks (`cdk.out/AwsSolutions-*-NagReport.csv`, one report per stack) with zero Non-Compliant findings.
